# Infrastructure and pipeline

- Polyrepo in the `pulse-pass` GitHub organization, `main` only, PRs from `feature/<ID>-<slug>`, merge commits only (squash and rebase disabled).
- `main` ruleset: active on the default branch, no bypass, blocks deletion and force push, requires a PR (0 approvals, merge method `merge`) and requires **every** CI job to pass (`lint`, `unit-tests`, `integration-tests`, `sonar`, `build`). It can be created with `gh api -X POST repos/pulse-pass/<repo>/rulesets`.
- SonarQube Cloud: organization `pulse-pass` (Free plan), project `pulse-pass_<repo>` with GitHub Actions analysis; `SONAR_TOKEN` is an organization secret shared by all repositories.
- `infrastructure/` holds `docker-compose.yml`, `.env.example`, `database.sql`, `service-start.sh` and `service-stop.sh`, plus the external `pulse-pass` network. The compose has `name: <repo>-test` and defaults for every variable the scripts export (`${SERVICE_PREFIX:-<repo>-test}`, `${MYSQL_HOST:-<repo>-test-mysql}`, `${PUBLISHED_API_PORT:-8082}`, `${ASAAS_URL:-${ASAAS_TEST_URL}}`), so `docker compose` without the script resolves to test mode (CI log step, manual commands); the scripts still pass `-p` and export those variables for `development`. The service keys of the compose are generic (`api`, `mysql`, `mockserver`) and the real name comes from `container_name` with `SERVICE_PREFIX`, because the key becomes a DNS alias on the `pulse-pass` network and both modes run together. Always address another container by its `container_name`, never by the compose key.
- `test` mode (`./infrastructure/service-start.sh test`, default, used by the CI) is self-sufficient: project `<repo>-test`, containers `<repo>-test-api`, `<repo>-test-mysql` and `<repo>-test-mockserver`, own MySQL (profile `test`, `database.sql` mounted in `initdb`) and MockServer, API on `API_PORT` (8082); it never depends on `pulse-pass-infrastructure`. The MySQL healthcheck pings over TCP (`mysqladmin ping -h 127.0.0.1`) so it only passes after `database.sql` has run.
- `development` mode starts only the API: project `<repo>`, container `<repo>-api` (the name other services use in `<NAME>_DEVELOPMENT_URL`), published on `DEVELOPMENT_API_PORT` (8092), using the shared `pulse-pass-mysql` (host `pulse-pass-mysql`, port 3306) from `pulse-pass-infrastructure`. Before anything else, the script requires that container to be `healthy` (otherwise it exits asking to start the shared infrastructure, without having stopped the running API: the check comes before `service-stop.sh`) and, as root (`MYSQL_ROOT_PASSWORD`, `root` like the infrastructure), creates the `.env` user with `CREATE USER IF NOT EXISTS` and a `GRANT ALL PRIVILEGES` only on the service schema, then applies `database.sql`. `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE` are interpolated into SQL, so they must not contain quotes or backslashes. Table changes only reach the shared MySQL when the script runs again; it is idempotent and never recreates what exists.
- Both modes can run at the same time (distinct projects, container names and ports). `service-stop.sh [test|development]` (default `test`) tears down only that mode's project (`down -v --remove-orphans --rmi local`) and never touches `pulse-pass-mysql` or the schema; `service-start.sh <mode>` calls it for the same mode first.
- Redis and Kafka are added to the compose (test mode, own containers) and to `.env.example` (development uses `pulse-pass-redis` and `pulse-pass-kafka`) only in the task that makes the service use them. The ports 3306, 6379, 9094 and 8180 belong to the shared infrastructure and the service must not publish them.
- The mode comes from the argument of the scripts, never from editing `.env`: each external dependency has a `<X>_TEST_URL` / `<X>_DEVELOPMENT_URL` pair in `.env`, and the script exports `<X>_URL`. The test URLs point to the `<repo>-test-mockserver` container.
- The start script creates the `pulse-pass` network if missing and copies `.env.example` on first run.
- Redis, Kafka, Kafka UI, Keycloak, Mailpit and MinIO live in the `pulse-pass-infrastructure` repository, created only when a task needs it.
- README: running the service only needs Docker (the image builds with its own JDK); Java 21 is only needed to run `./mvnw` (lint and tests) outside the container.
- Workflows: `pull-request.yml` (name `CI`) and `publish.yml` (name `Publish`, never "release"). Third-party actions are pinned by full commit SHA with the version in a comment (Sonar rule S7637); `actions/*` may use tags. The `sonar` job runs with `-Dsonar.qualitygate.wait=true`, so a failed quality gate fails the job and skips `build`.
- Pipeline: PR with lint (Checkstyle) → unit tests (JaCoCo) → integration tests (through `service-start.sh test`) → SonarQube Cloud → image build; on merge, version from the commits, `vX.Y.Z` tag and image on GHCR.
